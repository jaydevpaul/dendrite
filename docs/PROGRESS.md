- **§8.4's "~3" is a fidelity tier, not a bound on the walk.** The single
  most consequential finding of the session, and it would have quietly gutted
  §7's eval. §8.4 says composition "walks a *bounded* depth (~3)"; read as a
  hard cap on the query, §5's `FullInheritance` — "the **entire ancestor
  chain** at full text" — is unbuildable, and `HierarchicalDecay` ("span full +
  parent full + **older ancestors summarized**") has no older ancestors left to
  summarize, so it becomes byte-identical to full inheritance and §7 would be
  comparing five strategies of which three are secretly one. Compounding it,
  message-as-node means one exchange is *two* rows, so three ancestors is one
  and a half exchanges of history.
  The three numbers are now named separately: the CTE climbs to the root
  (runaway guard 200); the *strategy* decides how many ancestors reach the
  prompt; the *decay function* decides how many arrive at full fidelity, and
  that is where the `~3` lives. Depth is cheap because the recursion carries
  only `(edge_id, message_id, depth)` — content and anchors are joined out once
  at the end — so distant ancestors are expensive in *tokens*, not query time,
  which is the decay function's problem and not the walk's.

- **Strategy resolution never crosses a branch boundary.** §5 ("branches
  default to SpanOnly at creation") and §6 ("null override → keep walking →
  conversation default") pointed different ways for the commonest case of all:
  an anchored edge with a null override, which is what B1 writes when the
  client sends none. The reconciliation is in §6's own table, which permits
  null "on continuations **and on branches that accept the default**" — so null
  on a branch means something, and §5 says what it means. The rule:
  | Situation | Answer | `source` |
  |---|---|---|
  | no parent edge (root) | conversation default | `conversation_default` |
  | own parent edge anchored, override null | **SpanOnly** | `branch_default` |
  | nearest usable non-null override | that override | `edge` |
  | branch boundary, nothing usable | conversation default | `branch_boundary` |
  | root reached, no hit | conversation default | `conversation_default` |
  | safety cap fired | conversation default | `depth_cap` |
  "Usable" excludes exactly one value: `SpanOnly` seen from below, since §5
  locks it "valid on branches only" and a continuation two levels inside a
  SpanOnly branch resolving to it would compose the branch's span and drop
  everything typed in the branch since.
  Three consequences, all wanted: a branch is a deliberate context reset, so a
  trunk override should not reach across it (conversation-wide intent already
  lives in `default_strategy`); §6's "nested branches govern their own subtree"
  still holds, because an *explicit* override on a branch edge is inherited
  downward; and the walk is bounded by the distance to the nearest branch, so
  the only deep walk is in a conversation with no branches at all.
  It also needs no special case in SQL — the recursion continues only while the
  row just found was a continuation carrying no override, and app code reads
  whatever it stopped on.

    quality-per-token. That was wrong: a term that varies with the treatment is

## 2026-09-06 — Layer C built: C4 (HierarchicalDecay), plus a correction to C3's reader

**Sitting C4 built.** `HierarchicalDecay` in `app/context/strategies.py`, behind
the same interface as the other three. Suite is **250 passing**, up from 230.
Assembly, as planned — nothing new was invented; `Fidelity`, `DecayFunction`,
`TieredDecay`, `load_summaries()`, `summarised_turn()`, `SUMMARY_MISSING` and
`SUMMARY_MARKER` all came from C3 unchanged.

- **The shape.** `decay: DecayFunction = TieredDecay()` first, `name` second.
  Field order matters here in a way it does not for the other three, which have
  `name` as their only field: with `name` declared first,
  `HierarchicalDecay(TieredDecay(full_depth=1))` would put a `TieredDecay`
  instance into `strategy_used` and leave the tier at its default. `AnyStrategy`
  is a `Literal` hint and is not checked at runtime, so nothing would raise — the
  junk value would only surface later in the `generation.strategy_used` column.

  the steps marked `summary`, one `load_summaries()` call, then render
  nearest-first-reversed into prompt order with `full_turn` or `summarised_turn`.
  `ensure_leading_user_turn` at the end, same as `FullInheritance`.

  never appended per ancestor. Four short levels is one finding about one
  composition, and the eval reports a rate per run — a list holding the same name
  four times would have to be de-duplicated before it could be counted. Severity
  is not lost: `composed_context` stores the exact payload, so a later analysis
  can count which turns beyond the tier depth lack the marker.

  arm climbs to the root the way `FullInheritance` does, so a capped walk really

  manager rather than a fixture because it has to wrap the part of a test under

**A correction to C3's summary reader, decided this session.** `load_summaries()`
now excludes blank rows in the `WHERE`:

```python
func.btrim(MessageSummary.summary_text, " \t\r\n") != "",
```

- **Why exclude them at all.** A blank summary is not a cheaper version of the
  message, it is the message gone. Sending `[summarised]` with nothing after it
  would drop that ancestor from the prompt while the arm still counted it as
  covered — the coverage-for-fidelity confound the no-drop-tier rule exists to
  prevent.

- **Why in the `WHERE` and not in the dict afterwards.** `DISTINCT ON` keeps only
  the newest row per message. A blank written today would win on recency, become
  the message's summary, and then be discarded — taking a perfectly good older
  summary with it and costing full text for a message that had one. Excluded up
  front, the blank never competes. `test_a_blank_summary_does_not_beat_a_real_older_one`
  pins this, and it failed exactly that way before the fix.

- **Why the character set is spelled out.** Postgres's `btrim` trims **spaces
  only** by default. `btrim("  \n  ")` returns `"\n"`, which is not empty, so a
  newline-only summary sailed straight through the filter. The SQL was
  well-formed and the query ran — only the whitespace test caught the
  disagreement about what "blank" means. The empty-string test passed either way.

- This keeps "absent from the map means no summary" as the single definition of
  the rule, in the one place it already lived, and needs no special case in C4.

- **Written into §8.16 the same session**, alongside two corrections that
  belonged in the same passage: the ordering bullet said "`id DESC`, **not**
  `created_at DESC`" where the shipped reader has always ordered by both, and
  §9's `MessageSummary` annotation still described the reader as most-recent
  only. §12's "current summary selection rule" open item is now marked resolved
  — most-recent non-blank, `created_at DESC, id DESC`, model filter optional and
  off. No schema change anywhere: the exclusion is read-side, and `summary_text`
  stays `text NOT NULL` with the empty string still legal.

**Three fixes applied to hand-typed `app/` code** (the user asked for them
directly). `TieredDecay` without its parentheses as the field default — assigns
the class, so `self.decay.assign(steps)` becomes an unbound call with `steps`
landing in `self`; it raises, but reads like a problem with `assign`. In the
reader, `.where(` closed one clause early, making `query` a **tuple** of
`(select, boolean)` rather than a select. And the `btrim` default above.

**Two design questions raised and answered, neither built.**

- **Linear and exponential decay functions — not worth building.** With
  `Fidelity` being only `full | summary` there is no dial between the two levels,
  so every monotonic rule collapses to a single cutoff depth and all three
  produce identical prompts. They become meaningful only if fidelity becomes
  *graded* (several summary lengths), which needs `MessageSummary` to hold more
  than one summary per message per model — a change to locked section 9 for a
  second experiment the thesis does not need. Section 5's "linear, exponential,
  custom" is aspirational language written before D5 settled on two levels: the
  `assign(steps)` interface permits the family, the `Fidelity` type currently
  does not.

- **A fractional decay (`full_depth = ceil(len(steps)/3)`) — real, but rejected.**
  Unlike linear/exponential it does produce different prompts: on a 30-ancestor
  chain, three full versus ten. It was rejected because it reintroduces the very
  thing D5 avoided by choosing depth over token budget — a deep conversation
  would get more full text than a shallow one, so arm 4's token cost stops being
  a property of the strategy and becomes a property of which fixture it ran on,
  and averaging across fixtures averages things that are not the same
  measurement. Most of what it offers is available by sweeping
  `TieredDecay(full_depth=N)`, which keeps every run comparable. Eight lines in
  `decay.py` and nothing else changes if it ever earns its place.

**Open item raised against section 7 — hyperparameter selection is unspecified.**
`full_depth` is a constructor argument so the eval can sweep it, and D6's
`fraction` and `max_promotions` exist for the same reason — which gives arm 4 one
knob and arm 5 three, against zero for `FullInheritance`, `ParentOnly` and
`SpanOnly`. Sweeping on the same scenarios the results are reported from means
the tuned arms got N attempts and the baselines got one, and part of any margin
is then "we tried five things and kept the winner". The likely answer is a
tuning/reporting split — hold back roughly 8 of the 20–30 scenarios, sweep there,
freeze the values, then run all five arms once on the remainder. Cost argues the
same way: 25 scenarios × 5 arms × 3 repeats is 375 generations, and sweeping five
tier values across all of them doubles the run where an 8-scenario tuning set
costs 120. The sweep curve is itself worth reporting — a flat curve from
`full_depth` 2 to 6 would say the win comes from summarizing at all rather than
from where the line is drawn. **Not settled; needs a decision before the eval
harness is built**, and now logged as a §12 open item triggered on exactly
that, since it decides how the fixtures are split and cannot be retrofitted.

### C6 — `compose_context()`

**`app/context/compose.py`** is new and holds three things: `STRATEGIES`, a
module-level dict from strategy name to instance; `Composition`, a frozen
dataclass pairing the `ComposedContext` with the `StrategyResolution`; and
`compose_context()`, which looks the starting message up, resolves, walks, and
dispatches through the table.

**Dispatch is a lookup and the table is checked at import.** Two checks, both in
the module body: its keys must equal `ALL_STRATEGIES`, and every instance's own
`name` must equal the key it is filed under. The second one is not
belt-and-braces — the key is what was resolved and the instance stamps the
result, so those are two sources for one fact, and the mis-ordered-constructor
trap from C4 would put a `TieredDecay` in `name` without raising.

**Four shape decisions.**

1. **`SpanOnlyRequiresAnchor` escapes rather than being caught.** Decided after
   establishing that the state is forbidden by a *constraint*, not merely
   improbable: `ck_edge_span_only_needs_anchor` will not store a `SpanOnly`
   override on an unanchored edge, resolution can only answer `SpanOnly` for an
   anchored depth-1 edge, and that is the same edge `anchor_from_walk` reads.
   `max_depth=0` — the one way the walk could come back empty while resolution
   still said `SpanOnly` — is already rejected by `resolve_strategy`'s own
   `max_depth < 1` guard. So a fallback here would protect against nothing and
   could never be exercised. Compose runs before the streaming response, so an
   escape lands as a failed request with no blank row and no `Generation` row.
2. **A named wrapper, not a tuple and not a field on `ComposedContext`.** No arm
   can fill `source`, so putting it on the context would leave a hole every
   strategy ignores, and `as_payload()` stays exactly `system` + `messages`.
3. **No forced-strategy argument.** Section 7's harness names arms directly, so
   it does not come through here; adding one now would invent its shape *and* be
   the one thing that would make decision (1) reachable.
4. **`strategies` is a keyword with the module table as its default**, so a tuned
   set of arms can be handed in without editing the module.

**Three message lookups per compose, accepted.** `compose_context` needs the
`Message` for `StrategyRequest.question`, and `resolve_strategy` and
`walk_ancestors` each re-fetch it for their own `MessageNotFound`. Doing the
cheap existence check first means a bad id fails before two recursive CTEs run.
Threading a loaded message through B2's signatures to save two single-row
primary-key lookups was not worth it against a 1–2s budget.

**15 tests** in `tests/test_compose.py`. Beyond the four resolve-then-dispatch
cases: that `resolution.strategy` and `context.strategy_used` can *disagree*
(arm 5 with a dead embedder) and do agree on a clean run, so a composer that
always reported the simpler arm fails; that one `max_depth` reaches both
climbing queries (`depth_cap` **and** `walk_truncated` from a single call); that

### C7 — the generation service

**`app/services/generation.py`** is new: `start_generation()`,
`stream_generation()`, `PreparedGeneration`, `GenerationDone`,
`GenerationFailed`, `NotAUserMessage`, and two private writers.

**Two functions, and the split is forced.** Composition and the blank row can
both still refuse with a 404 or a 422; once a streaming response is returned the
status line is on the wire. A single async generator would not run its body
until the first iteration, by which point it is too late — so everything that
can refuse is in `start_generation`, and `stream_generation` runs with the
headers gone.

**Five shape decisions.**

1. **The role guard lives in the service**, raising `NotAUserMessage`, not in the
   route. The service is the thing that *creates* the blank assistant row, so
   putting the guard here means no caller can compose from one — including the
   eval harness, which never goes through a route.
2. **A failure logs the real exception and sends a fixed detail.** First logging
   in `app/` (`logger = logging.getLogger(__name__)`), which also gives D7's
   "and is logged" somewhere to go. Provider error text carries request ids and
   account details and this stream is browser-facing.
3. **The session factory is a parameter** defaulting to `async_session_factory`.
   D9 names that factory and it is bound to the *dev* engine, so a test of the
   completion write cannot reach the test database through it.
4. **`model_used` on a failed row comes from `settings.generation_model`** — the
   column is NOT NULL and the provider never got as far as reporting one. On
   success the provider's own value wins, same rule as the token counts.
5. **`conversation.updated_at` is bumped at the blank insert**, where
   `create_message` already bumps it, not in the completion write — that runs in
   another session and would have to re-load the conversation.

**A real bug found by a test, and it is a new standing gotcha.**
`assistant.updated_at = assistant.created_at` did **not** work. The two columns
are already equal from the insert, so the assignment is not a *change*, the ORM
left the column out of the SET clause, and `onupdate=func.now()` supplied
`now()` after all — `updated_at` came out 44ms ahead of `created_at`. Replaced
with an explicit `update(Message).values(content=..., updated_at=Message.created_at)`,
which cannot be optimised away and reads as what it is. This looks exactly like
the explicit-value-wins rule working, and the only symptom is a timestamp
slightly off.

**16 tests** in `tests/test_generation.py`, every write assertion read through a
second session because two separate commits are the whole pattern and only a
second connection can tell a committed row from one in an open transaction. The
gate test holds the stream open and asserts the message is still blank with no

### Two shape decisions, both asked before building

1. **The linear path is: continuation edges only, newest child at each step.**
   The API returns the whole graph as two flat lists, so a linear view has to
   pick a path. Continuation-only keeps anchored branches off the main path, so
   slice 4 cannot silently hijack this view. Newest-wins is what makes retry
   work: a retry writes a *second* assistant child of the same question rather
   than replacing the first, so the new attempt becomes the path and the
   abandoned one drops off it — counted on the question as "1 earlier reply not
   shown here", never hidden. Each step also reports its unshown replies and
   branches separately.
2. **An unanswered question or an unfinished reply gets an explicit button, and
   nothing generates on its own.** Both states are legal and both survive a
   reload (a blank assistant row reads `pending` forever). Generating on mount
   was rejected: reopening a thread whose generation keeps failing would call
   the model every time, and with a real key that is real spend.

### The rest of the slice

- **The list moved into the shell** so the app reads like a chat app. What is
  left at `/app` is the one thing a sidebar cannot do — name a new graph and
  open it. The API layer, hooks and row markup carried over unchanged. The
  title is still asked for rather than derived from the first message; nothing
  in the API names a conversation for you.
- **The shell owns the viewport height** (`h-dvh overflow-hidden`) so the
  thread scrolls in its own pane and the prompt zone stays put. Below `lg` the
  list is a drawer, not a stacked column — stacking would push the composer
  below the fold.
- **`stream.ts`**: `fetch` + `ReadableStream`, because the reply streams from a
  `POST` and `EventSource` only issues a `GET`. Decodes with `stream: true`
  (a multi-byte character split across two network chunks survives), splits
  frames on the blank line, normalises CRLF, `JSON.parse`s each `data:`,
  ignores unknown event names, and cancels the body in a `finally`.
- **`postStream` checks `response.ok`** and that check is meaningful: every
  status-code failure happens before the first byte. Once the stream is open
  the status cannot change and a failure arrives as an `error` event.
- **On `done` the graph is refetched *before* the live text is dropped.** The
  blank assistant row is inserted server-side after the last read and stays
  blank until the completion write, so clearing first would flash an unfinished
  reply between the last chunk and the refetch.
- **The route is keyed on the conversation id**, so switching conversations
  remounts. Without it a reply still streaming follows the user into the next
  conversation and renders there.
- **Run metadata sits under each reply** in mono: the arm that ran, why it was
  chosen (`source` mapped to a plain phrase), the model, and the provider's own
  token counts. Degradations render in `warn` — the semantic use that token is
  reserved for. Per-session by construction: nothing reads `Generation` rows
  back yet, so a reload shows no numbers rather than stale ones.
- **The textarea is never disabled**, only the send button. Disabling it would
  take focus away mid-reply and hand it back to nobody, and sending mid-stream
  would abort the reply still arriving. Enter sends, Shift+Enter breaks the
  line, and an IME's composing Enter is ignored.
- **The conversation detail page's facts** (created, updated, id) survived the
  rewrite inside a native `<details>` in the header — no dependency.

### Verified live, through the proxy on :5173

Fifteen steps: 401 with no cookie → 201 signup → 201 create → 201 root message
with `edge: null` → graph reads one message, no edges, `pending: false` →
generate streams `start` (`HierarchicalDecayWithRetrieval`,
`conversation_default`, `gpt-5.6-luna`), one `chunk` frame per chunk, `done`
with `74 in / 6 out` and no degradations → the stored reply is complete and its
`created_at` equals its `updated_at`, so it reads as never edited → a second
turn streams four frames → **regenerating the same question writes a second
assistant sibling, and the path walk picks it while reporting "1 earlier reply"
on the question** → 422 generating on an assistant message → 404 on an unknown
message id → 422 on whitespace-only content → 409 on a second root → 404 on
another user's graph → the conversation's `updated_at` moved past
`created_at`, which is the sidebar's sort key.

**The unfinished-reply state needed a different method.** The fake finishes
faster than a client can abandon it — `curl -m 0.05` disconnects and the server
still completes the write, because by then the reply is already collected. So a
blank assistant row and its edge were inserted straight into the dev database:
the API reported `pending: true`, the path walk resolved the gap as
"unfinished" and named the right question to retry, and the retry then took
over the path with the blank row counted off it.

`npm run build` typechecks clean and emits `conversation` as its own chunk
(17.4 kB). The write-up is in `docs/frontend_design.md` §8.

### Rendered replies, and the mapping that keeps anchors exact

The interesting part of the session. Slice 4's selection layer was built on the
DOM text being the stored text; the renderer breaks that, and the fix is
`source-spans.ts` stamping each verbatim run with its source offset. Full
write-up in `frontend_design.md` and 8.19.

**What the design turns on:** every stamp is verified against the source before
it is emitted, and anything that fails the check — an escape, a KaTeX formula —
becomes *atomic* rather than becoming wrong. A coarser anchor is a fine trade;
a wrong one is a 422 in the good case and a mark over the wrong words in the
bad one.

**Three silent failures, all found by using the app rather than by the tests:**

1. A branch off a formula resolved, counted as marked, and was therefore also
   left off the list of unmarked branches — reachable from nowhere. Marks now
   go round whole nodes, not only runs of text.
2. `MarkedSpan` replaces the element the renderer stamped, so it has to copy
   the stamp onto the mark it draws. Without it, one branch on a reply stopped
   branching working anywhere in that reply until reload.
3. Two boundaries with no stamped run around them fall back in opposite
   directions and cross, and a crossed pair returned null — which withdraws the
   offer with nothing on screen explaining why.

Number 3 is the one to remember as a *class* of bug: **the failure mode of this
whole layer is silence.** Nothing throws, the reply looks perfect, and
branching just stops being offered. That is why the load-bearing test is a
sweep over a kitchen-sink document asserting every measurable run contains
exactly the source text it claims, rather than a set of cases.

floated at the span. Inline meant scrolling away from the words being asked
about in order to ask about them. A centred modal with a blurred backdrop was
the alternative and is worse for the same reason — it hides the referent.

## 2026-09-09 — Frontend slice 5: the branch navigator, and branch delete

Written up from the working tree rather than from a session transcript — this
work was done in a separate chat, so what follows is what the code says, and
the reasoning is quoted from the comments the author left rather than
reconstructed. Anything that was decided and *not* written down in a comment is

### The navigator — `frontend/src/features/navigator/`

Five new files: `turns.ts` (302 lines, the tree build and its layout),
`turn-tree.tsx`, `turn-graph.tsx`, `navigator-panel.tsx`, and `turns.test.ts`
(15 tests). The panel is the right-hand column the record already settled on,
behind the `Network` switch now sitting beside the conversation title.

**A turn fuses a user message with its reply into one node, and the fusion
splits the moment a question has more than one reply.** The fusion is a
*rendering* choice only — the message is still the stored unit and still what
an anchor points into. Fusing is what makes an ordinary conversation draw as a
column of turns instead of a ladder of alternating half-cards; splitting on a
second reply is what keeps regeneration and the eval's five-arm fan-out
visible, since those are the cases message-as-node exists to represent.

**Layout is deterministic, and that is why there is no graph library.** Every
node has exactly one parent, so this is a tree: depth sets the row and a tidy
left-to-right sweep sets the lane. Nothing settles, so two screenshots of the
same conversation are identical — which matters for a project whose deliverable
is a published evaluation. `MAX_NODES = 2000` is a hard stop against a
malformed graph.

**Sibling ordering matches the linear walk.** `newestFirst` in `turns.ts`
breaks a `created_at` tie on `id`, the same rule `buildThread` uses, so the
navigator and the thread cannot disagree about which child is the current one.
Siblings drawn side by side use the reverse, oldest-first, because that is
reading order.

**Selecting is separate from going there.** A click selects; the footer, a
double-click and Enter open the path. Opening on every click would move the
thread under the reader while they were still looking around. The selection
lives on the panel rather than in either view, which is what lets the
tree/graph switch preserve it — both views draw from the graph the page already
has, so switching is a render and refetches nothing.

**`viewFrom` is carried down during the build, not recomputed by climbing.**
Each node knows what `?from=` has to hold for the linear view to show it,
because the build already knows which view it is inside.

### Both side panels are resizable

`frontend/src/lib/panel-size.ts` and `frontend/src/components/ui/resize-handle.tsx`.
`SIDEBAR_BOUNDS` is 264 default / 200–460, `NAVIGATOR_BOUNDS` is 320 / 240–620
because the graph is the widest thing in the app.

**Width is stored per browser; the navigator's open state is stored per user.**
Deliberately different, and both are argued in the files: a width is a fact
about the window it was dragged in, so carrying 420px from a monitor onto a
laptop would be restoring a preference nobody has — while "remember it open" is
a habit, and two people sharing a browser should not inherit each other's. The
open state is still `localStorage` rather than a stored preference, so it is
per user *per browser*; inventing a preferences endpoint for one boolean was
not worth a column.

**Every width is clamped against the viewport as well as its own bounds**, with
a `THREAD_FLOOR` of 420px. A panel dragged wide on a big monitor cannot squeeze
the thread to nothing on a small one.

`readNavigatorOpen` is read synchronously in a `useState` initialiser and never
in an effect — read in an effect and the panel renders closed and jumps open on
every load. `useMe` can resolve a beat late on reload, so an effect re-reads
once the id arrives, guarded on a ref so it runs once.

### Branch delete — `DELETE /conversations/{id}/messages/{message_id}`

`delete_branch()` in `app/services/message.py`, the route in
`app/api/routes/messages.py`, 14 tests in `tests/test_branch_delete.py`.

**Only a branch can be deleted.** Two refusals, both 422 via `NotABranch`: the
conversation's root, because deleting that is deleting the conversation and
that has its own route; and a continuation, because deleting a message in the
middle of a thread would silently take the rest of the thread with it. A
message outside the conversation is `MessageNotInConversation` → 404, the same
answer and the same reason as everywhere else.

**The messages are deleted explicitly, not by cascade, and the reason is
structural.** A message does not point at its parent — the edge does. So
deleting one message takes its edges with it and leaves its children as
messages nothing points at, and *a message nothing points at is exactly how the
root of a conversation is identified*. Cascading would produce a conversation
with several roots and a thread that walks whichever it found first.

**`_descendant_ids` is a recursive CTE joining on `parent_message_id`** — the
exact opposite of the ancestor walk, where joining on that column is the bug
that hangs. Going down, the fan-out is the point. Both the seed and the
recursive step filter `conversation_id` inside the CTE, for the same reason the
ancestor walk does. `SUBTREE_SAFETY_CAP = 200` mirrors the walk's guard. The
final `DELETE` re-states the conversation filter as belt and braces, so a bug
in the walk is a no-op rather than a cross-conversation delete.

On the client, `useDeleteBranch` **invalidates rather than patches**: the delete
takes a whole subtree, and working out locally which rows went would be
re-implementing the server's walk somewhere it can drift. The conversation list
is invalidated too, since its ordering and its count both just moved. The
confirm dialog from the sidebar delete is reused.

### `plainPreview` — `frontend/src/features/messages/preview.ts`

13 tests. Anywhere a reply is **quoted rather than read** — a navigator row, a
graph card, a branch crumb, the span above the branch composer — it has to be
plain text, or the reader is shown `**attention layer**` and
`\[ \text{score}(Q,K) = QK^T \]` where a phrase belongs. That is the same
failure as not rendering a reply at all, only in miniature.

Deliberately **not** a markdown parser: a preview has no structure, so what is
wanted is the words with the syntax taken off, and running the real pipeline
would mean rendering to a DOM and reading its text back for every row in a
list. Also deliberately **only** for previews — nothing anchored is computed
from its output, so it can rewrite as freely as it likes with no risk of moving
a branch.

Maths is stripped first, and that order is the one thing in the file that is
not arbitrary: `\[` is a LaTeX delimiter to this app, but read as markdown it
is an escaped bracket, so anything handling escapes earlier would leave the
brackets in and the formula wrapped in them. Applied at five call sites in
`message-turn.tsx` and `conversation.tsx` — the branch popover, the unmarked-
branch list and its title, the branch composer's quote, and the branch trail's
crumbs and titles.
